## 1. ContextResolver: exact contract + existing reuse
Interface it must satisfy (planning.py:27-36): `async resolve(*, question, identity, route_hint) -> ContextBundle`.
Only caller: context_node (engine.py:153-217). Hard constraints from that caller:
- route_hint is **hard-coded "standard"** (engine.py:166), and the pre-route timeout is computed from the standard route (engine.py:991-1003). So ContextResolver never receives a fast hint today.
- Exceptions → stop_reason context_compilation_failed / context_deadline_exceeded (engine.py:168-196).
- Returned ContractContextBundle fields (contracts.py:123-160): semantic_release_id UUID, schema_snapshot_id UUID, domains (1..8, min1), asset_ids (1..20, min1), approved_relation_ids (<=8), approved_edge_ids (<=16), resolution_status, unresolved_slots, conflict_ids, degradation_flags, token_cost, evidence_count.

**Do not duplicate the machinery — it already exists and needs no new resolver class:**
- `SemanticContextResolver` (context_compiler.py:156-250) already adapts release-scoped evidence → ContractContextBundle, including domain/relation/edge projection (194-217) and resolution_status derivation (232-236). It is tested at test_plan_pipeline.py:838-863.
- `ContextCompiler` (context_compiler.py:87-153) already does release-scoping + RRF fusion + budgets (reciprocal_rank_fusion:78-84; _BUDGETS:22-26; _RELATION_LIMITS:28), and `release()` returns the exact bound release (150-153).
- The ONLY missing production collaborator is a concrete `PolicyScopedEvidenceProvider` (Protocol context_compiler.py:65-71; zero src implementations). It must return `PolicyScopedEvidence` (50-63): lexical/vector/graph Evidence tuples, embedding_available, resolution_status, unresolved_slots, conflict_ids, degradation_flags. `Evidence.metadata` must carry `domain` and either `relation_id`/`asset_type=relation` or `edge_id`/`asset_type=join` (context_compiler.py:265-280).

**Production-reuse gap that must be resolved:** `ContextCompiler.__init__` takes a `SemanticRegistry` (context_compiler.py:88) and uses `active_release()`/`get()` — an **in-process** class (registry.py:117-222). The production release lives in control-PG and is read via `ControlSemanticReleasePublisher.read_active()` (registry.py:478-556). read_active returns a `SemanticRelease` that is not registered in a SemanticRegistry, so `ContextCompiler.release()` would raise. The resolver needs either a duck-typed registry adapter over read_active (both methods, no isinstance check) or a load-into-SemanticRegistry step. Also read_active selects only semantic_documents (registry.py:504-512) — it does NOT read `semantic_aliases`.

**Reusable retrieval source:** `retrieve_active_semantic` (retrieval.py:25-64) already does active-release read + lexical + vector + graph-hint fusion, but (a) its only caller is the legacy `agents/sql_agent/agentic_rag.py:40,93`, (b) it takes no identity (no policy scoping, contrary to the Protocol docstring "already filtered for the request identity"), and (c) it cannot produce resolution_status/unresolved_slots/conflict_ids — a new provider must add candidate-count → resolution_status logic (1 candidate → resolved, >1 → ambiguous, 0 → incomplete) and missing-slot detection (see §3).

## 2. Deterministic zero-model QueryPlanProvider — concrete obligations
Input (planning.py:45-51): `propose(*, question: str, context: ContextBundle, identity: RequestIdentity) -> QueryPlan`; class attr `is_deterministic = True` (engine.py:113-118 rejects False). No model calls allowed pre-route.
Return: `QueryPlan` (contracts.py:163-208): intent ∈ {metric,trend,comparison,ranking,detail}; domain (str); metric_keys (1..16, but see below); dimensions; filters (BoundFilter); **required** time_range (TimeRange, contracts.py:58-71 — start,end mandatory); grain; source_strategy; result_limit (ranking only); required_permissions; unresolved_slots.
Must call / reuse (file:line):
- release + docs: `ControlSemanticReleasePublisher.read_active()` (registry.py:478) or `SemanticRegistry.active_release()` (registry.py:132).
- metric document identity: document_id == `MetricContract.asset_id` == `"metric."+metric_key` (metric_contract.py:91-93; materialization.py:107-123; inventory_release.py:632). **QueryPlan.metric_keys must be asset_ids ("metric.<key>"), because MetricQueryCompiler matches `doc.document_id == plan.metric_keys[0]`** (metric_query.py:241) and MetricAuthority does exactly that (metric_fixtures.py:116,139).
- metric classification/metadata: document metadata asset_type/domain/status/execution_contract (materialization.py:111-120); parse `execution_contract` via `MetricContract.model_validate_json` (metric_query.py:246) for supported_grains/supported_dimensions/required_permissions.
- semantic alignment with validator: PlanValidator requires `plan.domain in context.domains` and `set(plan.metric_keys) <= set(context.asset_ids)` (planning.py:130-147). So the provider must pick the metric from the SAME evidence the resolver returned; ContextBundle loses asset_type/metric_key metadata, so the provider must either re-read the release or share the resolver's lookup (a design coupling, not an accident).
- exact identity/lifecycle resolution can reuse `MetricIdentityIndex.try_resolve` (inventory_release.py:263-320) and `load_authoritative_inventory` (authoritative_sources.py:77-89) — but see §3: that index is exact-key only.
- alias normalization helper exists: `normalize_semantic_alias` (materialization.py:144-146); aliases per metric are materialized (materialization.py:442-447) and persisted (registry.py:830-849), **but nothing reads the semantic_aliases table anywhere in src** (single grep match = the INSERT itself).
- time range: no parser exists (see §3), so the provider must own a deterministic relative/absolute date grammar or require an explicit slot.

## 3. Is a deterministic QUERY path possible today? — No, not for general NL; yes only for a narrow bounded grammar
Concrete blockers:
- The only metric-inventory resolver is exact-key-only: `MetricIdentityIndex.try_resolve` explicitly says "Exact identity only: no strip, case-fold, prefix, or alias matching" (inventory_release.py:274-298). It resolves key→lifecycle, never utterance→key.
- The inventory's own display labels collide across namespaces; the P1 bridge must exclude collided members (inventory_release.py:14-21, 484-527). So name→key is not even injective in the authoritative inventory.
- Runtime retrieval is Postgres FTS over document content (`d.lexical @@ websearch_to_tsquery('simple', :query)`, registry.py:569); it ranks but does not return a unique metric and is not used by any typed-path code.
- The legacy deterministic matcher `MetricSemanticLayer.resolve` (metric_layer.py:18-33) scores metric_code/display_name/tags, but it reads the non-release table `v_metric_metadata` via DatabaseManager (metric_layer.py:119-137) and has **zero callers in src** — it is neither gateway-governed nor bound to the release/asset-id namespace.
- QueryPlan.time_range is mandatory (contracts.py:174) and no date library is imported anywhere (`dateparser|parsedatetime|relativedelta|dateutil` = 0 hits in src). "Today/this month/2026-01" resolution does not exist.
- Organization filters/ranking cannot be planned: `metric_query.py:684` requires org filter `source == "entity_alias"`, but nothing in src produces `source="entity_alias"` (only the Literal at contracts.py:97). docs-pr07a-slice2.md:28 confirms "本切片不做自然语言规划、alias 查询或名称到 ID 的转换".
- Only one product metric catalog exists, with BOTH metrics `pending_source` (config/metrics/complaint.yaml:7,26) — so there is no activatable executable metric seed today.
Verdict: a deterministic zero-model provider is feasible ONLY if P4-S1 defines a **narrow, explicit supported QUERY grammar** (e.g. exact display-name or metric-key token match within the resolved release evidence → exactly one metric; explicit/relative date phrase from a small deterministic table; city_company scope only; single metric). Anything not in that grammar must return a plan with unresolved_slots / a schema-valid "unsupported" outcome so PlanValidator yields clarify and the graph stops. A model-assisted PROPOSAL path is NOT a substitute for the pre-route provider (engine.py:113-118) — it can only live post-route (§4). The plan's P4-Q (§8.5.1) only requires a "快速问询" closure, which a narrow grammar satisfies; full NL planning is explicitly out of PR07A scope (docs-pr07a-slice2.md:28,58).

## 4. after_route (engine.py:826-831) — exact change, fail-closed, and the P4-S2 return path
Current gate: `if typed_pipeline_enabled and _route(state) == "fast": return "compile"; return "model"` (826-831). Consequences: standard/deep never reach compile (826-831) even when the plan validated as allow; and `model_node` sends only the question (engine.py:669) — it never sees the QueryPlan/context.
Required change (P4-S1):
- Replace the route literal with a predicate on the **validated query plan**: compile when `typed_pipeline_enabled` AND `state["query_plan_validation"].outcome == "allow"` AND the plan's hashes match (the same check execute_node already re-does, engine.py:515-519). Keep an optional explicit route allowlist (fast+standard for QUERY) if mode budgets require it.
- Fail-closed is already structurally preserved: any provider/context/validation failure sets `stop_reason` (engine.py:178-196, 245-259, 319-345, 433-442), and after_route returns `__end__` before the route test (engine.py:827-828). Do NOT add a model fallback for failed typed requests.
- STANDARD/DEEP later return to the same authority via a **post-route proposal node**, not by widening model_node:
  1. `route(standard|deep)` → new `propose` node (only when typed_pipeline_enabled) that calls `model_gateway.invoke` with a structured QueryPlan response schema (ModelRequest stage="plan", engine.py:666-676) and yields an **untrusted** QueryPlan.
  2. Edge `propose -> validate` re-uses the SAME `validate_node` / `PlanValidator` (engine.py:278-345), then `compile -> execute`.
  3. For deep/BUILD, insert the existing `hitl_node` between validation and compile so the approved object is the typed plan, and add the missing `hitl -> compile` edge — today `hitl` is terminal: its only edge is `model -> hitl` (engine.py:868) and `after_model` routes only hitl/END (engine.py:836-837).
  4. `PlanExecutor` must never receive model output: it only accepts a typed ExecutionPlan built by PlanCompiler from an `allow` PlanValidationRecord (engine.py:530-540; planning.py:302-317). This is already the invariant; the proposal path must not bypass it.
- Note the checkpointer/state consequence: `model_node` currently writes `pending_answer`/hitl fields (engine.py:748-759) but stores no plan; a proposal node must checkpoint the QueryPlan + its validation record (V2EngineState already has query_plan/query_plan_validation, engine.py:57-58).

## 5. PlanCompiler step vocabulary — S1 vs S2
P4-S1 (QUERY) strictly requires **no step-vocabulary extension**. The supported path is `FetchMetricStep("fetch_metrics") + VerifyStep("verify_result")` (planning.py:319-335), which exactly matches MetricQueryCompiler's single-metric contract (metric_query.py:229) and the runner's `step.metric_keys == query_plan.metric_keys` check (metric_query.py:557). One constraint to encode instead: the provider must emit exactly ONE metric_key, because MetricQueryCompiler rejects len != 1 (metric_query.py:229) even though PlanCompiler would accept up to 16 (contracts.py:233).
P4-S2 / BUILD / ANALYZE items (not S1):
- TrustedCalculationStep is **never produced** by PlanCompiler (planning.py:319-335) and QueryPlan carries no template_id field (contracts.py:163-208), so BUILD needs a QueryPlan contract extension + compiler emission + `PlanValidator(approved_template_ids=...)` provisioning. Defaults make this fail-closed: `PlanValidator()` has `approved_template_ids=frozenset()` (planning.py:71), so any TrustedCalculationStep → outcome "approval" (planning.py:261-270). `metric_plan_executor` also builds PlanExecutor without a trusted_calculation_runner (metric_query.py:633-635), so such a step would fail `trusted_calculation_unavailable` (execution.py:363-364).
- ANALYZE detail/branching has **no PlanStep kind at all**: the union is only FetchMetricStep | TrustedCalculationStep | VerifyStep (contracts.py:281-284). `source_strategy="detail_required"` is a QueryPlan field (contracts.py:176) that reaches the validator (planning.py:164-179) but is never compiled into a distinct step. A genuine detail/exploration step is P7A material.
Correction to prior doc: "detail steps are consumed by PlanExecutor" is false — there is no detail step type (see §CORRECTIONS).

## 7. Recommended P4-S1 slicing (≤3, each with its own exit test)
**Important structural constraint on any split:** create_v2_engine rejects *partial* wiring — `typed_pipeline_requested and not typed_pipeline_enabled → ValueError` (engine.py:109-112). You cannot wire just context_resolver or just query_plan_provider. So the first slice must either deliver all three together, or first relax this guard. Recommended:
- **S1a — "Deterministic QUERY plan authority" (no container change).** Build the concrete PolicyScopedEvidenceProvider + narrow-grammar deterministic QueryPlanProvider; wire SemanticContextResolver + provider + metric_plan_executor in a test/fixture composition. Exit: engine-level test (existing MemorySaver pattern) routes a supported QUERY fast→compile→execute through GatewayMetricStepRunner with model_calls==0 and a control conversation for unsupported→clarify.
- **S1b — "Activate in AppContainer + broaden after_route."** Pass all three collaborators in container.py:119-123; change after_route to compile on validated allow plans (fast+standard); keep unsupported fail-closed; extend test_model_architecture.py; add readiness/degradation if the release is absent. Exit: the Docker integration test in §6.4 plus a permission-denied/unsupported no-SQL/no-model test.
- **S1c — (optional) "Model PROPOSAL re-entry skeleton."** Only if P4-S1 is to prepare STANDARD/DEEP: add the post-route propose→validate→compile path with the model producing an untrusted QueryPlan, and add the deep HITL→compile edge. Exit: an invalid model proposal is denied by the same PlanValidator and never reaches PlanExecutor; a valid one compiles. (This is arguably P4-S2 scope and can be deferred.)
